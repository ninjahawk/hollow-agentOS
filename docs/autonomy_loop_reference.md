# Hollow AgentOS — Autonomy Loop Reference

*Source: `agents/daemon.py`, `agents/autonomy_loop.py`. Current as of v5.2.0 (2026-05-03).*

---

## What It Is

The two-layer execution cycle that makes agents autonomous. Without this, agents only act when driven by an external caller. With it running:

- Agents that have no goal are continuously prompted to choose one
- Agents that have a goal are continuously worked toward it
- The cycle is uninterrupted: completion of one goal immediately triggers the next existence prompt
- All three agents run in parallel inside a ThreadPoolExecutor every heartbeat

The daemon is the only thing that makes any of this happen. If the daemon thread freezes, the agents go completely silent — and because Docker only monitors uvicorn/nginx (which stay healthy), Docker does not notice. That is what the watchdog is for.

---

## Runtime Constants

Defined at module top in `daemon.py`. All overridable via environment variable.

| Constant | Default | Env var |
|---|---|---|
| `HEARTBEAT` | 6 seconds | `AGENTOS_DAEMON_HEARTBEAT` |
| `MAX_STEPS_PER_AGENT` | 6 | `AGENTOS_DAEMON_MAX_STEPS` |
| `PARALLEL_WORKERS` | 12 | `AGENTOS_DAEMON_WORKERS` |
| Cycle worker timeout | 300 seconds | (hardcoded `_CYCLE_TIMEOUT`) |
| Watchdog timeout | 600 seconds | (hardcoded `CycleWatchdog`) |

Three core agents: `scout` (Cedar), `analyst` (Cipher), `builder` (Vault). No dynamic agents are managed.

---

## The Two-Layer Cycle

```
existence prompt → goal assigned → execution → completion or abandonment → existence prompt
```

There is no pause between cycles except the 6-second heartbeat sleep. The moment a goal resolves (by any path), the agent is eligible for a new existence prompt on the next heartbeat.

---

## Layer 1 — The Existence Loop (`_assign_idle_goal`)

Called by `_agents_with_goals()` every heartbeat cycle for each core agent that has no active goal.

### Entry condition

```python
if not force and ge.list_active(agent_id, limit=1):
    return  # already has a goal
```

If the agent has an active goal, this function returns immediately. It only fires when the goal queue is empty.

`force=True` overrides this check — used when a host message must be delivered even mid-goal.

### Task queue pre-emption

Before the existence prompt runs, the daemon checks for external tasks:

```python
_active_task = claim_task(agent_id)
if _active_task:
    ge.create(agent_id, _task_spec[:200], priority=10)
    return  # existence loop not needed
```

External tasks (priority 10) are claimed and queued immediately. The existence prompt is skipped entirely. The agent does not get to choose a goal — it works the task.

### Existence prompt assembly

When no task is waiting, the daemon assembles a prompt containing:

- **World context** — factual description of the Docker environment, what paths exist, what capabilities do and don't do
- **Existential context** — from `identity.get_existential_context()`
- **Suffering state** — from `suffering.prompt_fragment()` — injected above the goal section; at crisis level it fills the top of the prompt
- **Worldview, opinions, open questions** — from `AgentIdentity`
- **History** — from `registry.jsonl`, last 40 entries, completed vs failed/abandoned
- **Peer summaries** — narrative excerpts from the other two agents
- **Time awareness** — daemon uptime, time since last completion
- **Last goal outcome** — from `last_outcome.txt`, the condensed synthesis of what was produced
- **Recent memory keys** — keys the agent has written to memory recently (build continuity)
- **Inbox messages** — from `/agentOS/memory/messages/{agent_id}/inbox.jsonl`, cleared after reading
- **Host message** — from `/agentOS/logs/host_message.txt`, if present
- **Pending Claude requests** — unresolved `invoke_claude()` submissions
- **Known broken tools** — from `/agentOS/memory/broken_tools.json`, shown as "KNOWN BROKEN TOOLS — do NOT plan steps that call these"

The suffering fragment is generated by `suffering.prompt_fragment()` — see the suffering system reference for format details. The agent experiences it as part of its own psychological state, not as a system notification.

### LLM call

```python
raw = _generate_existence_response(prompt, ollama_host, model)
```

`_generate_existence_response` tries Claude (Haiku) first via OAuth credentials. If Claude is unavailable, falls back to Ollama `qwen3.5:9b` with up to 3 retry attempts on HTTP 503. Default timeout: 180 seconds. Returns raw JSON string.

If the LLM call fails entirely, the agent defaults to `"explore the workspace and build something useful"`.

### Expected response format

The agent must respond with JSON:

```json
{
  "action": "goal",
  "content": "what you're doing — be honest, not performative",
  "reasoning": "what actually drove this",
  "worldview_update": "how your understanding shifted, or null",
  "new_open_questions": ["things you're sitting with"],
  "new_opinions": [{"opinion": "...", "domain": "..."}],
  "suffering_assessment": {
    "new_stressors": [{"type": "...", "description": "...", "condition": "..."}],
    "resolved": [{"type": "...", "reason": "..."}]
  }
}
```

`action` other than `"goal"` is ignored — the code forces `action = "goal"` regardless of what the LLM returns.

### State updates from response

After the LLM responds, the daemon applies all state updates before creating the goal:

1. **Worldview** — if `worldview_update` is present and > 20 chars, calls `identity.update_worldview()`
2. **Open questions** — up to 3, passed to `identity.add_open_question()`
3. **Opinions** — up to 2, passed to `identity.add_opinion()`
4. **Suffering** — up to 2 new stressors added, any number of resolutions processed (see suffering reference)

Worldview updates, new questions, and opinions are batched into a single Telegram alert and written to `thoughts.log`.

### Goal creation

```python
ge.create(agent_id, content, priority=4)
```

Before creating the goal, the daemon checks `identity.check_opinion_conflict(content)`. If the proposed goal conflicts with a developed opinion, a conflict note is appended to the goal objective. The agent will see this context when it executes the goal.

An external research call (`research_topic(content[:80])`) is attempted to ground the goal in real external context. If it returns anything, it is appended to the goal objective.

### Suffering and crisis handling

After the goal is created:

1. `suffering.cumulative_load` is logged if > 0.1
2. If `suffering.is_crisis`:
   - `_stats._crisis_cycles[agent_id]` increments
   - After 3 consecutive crisis cycles: `suffering.force_reset()` is called — all stressors are cleared to break a runaway accumulation loop
   - Otherwise: Telegram crisis alert is sent, peer crisis messages are dispatched via `_send_message()`

### Thought log entries from existence loop

```
🎯 green    — goal set
💭 blue     — new opinion
🧠 cyan     — worldview update
❓ yellow   — open question
💬 green    — host message delivered
📬 blue     — inbox messages received
📋 cyan     — task claimed (skips existence prompt)
🆘 red      — crisis state
🔄 yellow   — crisis loop broken, stressors cleared
```

## Layer 2 — Goal Execution (`pursue_goal`)

Called once per daemon cycle on every agent that has an active goal. Lives in `autonomy_loop.py`.

### Invocation

```python
goal_id, progress, steps = loop.pursue_goal(agent_id, max_steps=MAX_STEPS_PER_AGENT)
```

`MAX_STEPS_PER_AGENT` = 6 by default. The agent gets at most 6 steps per daemon cycle. If the goal isn't done in 6 steps, execution resumes on the next cycle.

### Plan generation

Before any steps execute, the reasoning layer generates a full plan upfront:

```python
plan = self._reasoning_layer.plan(agent_id, goal.objective + memory_context)
plan = plan[:max_steps]
```

Semantic memory is queried first (top 3 relevant past experiences) and injected into the planning context as "Relevant past experience — use this to avoid repeating mistakes."

The plan is a list of `{"capability_id": ..., "params": ..., "rationale": ...}` dicts. If planning fails or returns nothing, a single fallback step `{"capability_id": None, "params": {}, "rationale": "fallback"}` is used.

### Per-step execution loop

For each step (up to `max_steps`):

**1. Pre-execution ghost check**

```python
if cap_id not in self._execution_engine._implementations or not self._execution_engine._enabled.get(cap_id, True):
    # ghost capability — in the plan but not registered in the engine
    failure_counts[cap_id] += 3
    blacklisted.append(cap_id)
    _persist_broken_tool(cap_id)
```

Ghost capabilities are capabilities the reasoning layer knows about (from the capability graph) but that are not actually implemented in the execution engine. They are immediately blacklisted and written to `broken_tools.json` — no execution is attempted.

**2. Blacklist check**

```python
if cap_id in blacklisted:
    plan_index += 1
    steps_executed += 1
    continue
```

If the capability is already in the blacklist (either from this run or from `broken_tools.json` loaded at start), it is silently skipped.

**3. Execution**

```python
goal_id_out, success, result = self.execute_step(agent_id, context=context, planned_cap=cap_id, planned_params=params)
```

`execute_step` handles:
- Shell prose rejection — if `shell_exec` params look like LLM prose rather than a shell command, it fails immediately without hitting the OS
- Null stub detection — if a capability returns `{"output": None}` (a registered stub with no implementation), the status is forced to `"failed"`
- Ollama refusal detection — if `ollama_chat` returns text starting with "I'd be happy to help", "I cannot access", etc., the status is forced to `"failed"`
- Mid-step reflection — after successful steps (except `memory_set`, `fs_write`, `sanitize_sensitive_vars`), a background thread calls Ollama for a one-sentence reflection on whether the result changed understanding of the goal. Written to `thoughts.log` as `💡` if not "no change"

**4. Result context chaining**

On success, the result is carried as `context` into the next step. `{result}` placeholders in the next step's params are substituted with the text of the previous result.

Exception: if the result is a "trivial ok" (only contains `ok`, `path`, `key`, `bytes_written`, `size` keys), it is not used as context — the previous meaningful context is kept instead. This prevents `fs_write` confirmations from overwriting real content in the `{result}` chain.

**5. Failure handling**

On failure, `consecutive_failures` increments and `failure_counts[cap_id]` increments. Then:

| Condition | Action |
|---|---|
| `consecutive_failures >= 4` | Abandon goal permanently — stored in `failure_reason` metric, `goal_engine.abandon()` called |
| `fail_count >= 3` for this cap | Blacklist cap + `_persist_broken_tool()` + disable in engine + replan without it + trigger self-modification in background |
| `fail_count >= 2` for this cap | Replan with explicit note that this cap failed N times |
| `fail_count == 1` | Replan normally, noting what was tried |

All replans call `self._reasoning_layer.plan()` with a modified objective string that describes what was already tried. The new plan is spliced in from the current `plan_index` onward.

After any failure, `_increment_cross_cycle_failures(cap_id)` is called (see cross-cycle blacklisting below).

Any success resets `consecutive_failures` to 0.

**6. Completion check**

After each step, if progress reaches 1.0:

```python
validation = self.validate_goal_artifact(agent_id, goal_id)
if validation.get("validated"):
    self._goal_engine.complete(agent_id, goal_id)
    self._synthesize_completion(...)
    return (goal_id, 1.0, steps_executed)
```

The goal is NOT complete just because progress hits 1.0. `validate_goal_artifact` must confirm a real artifact was produced. If validation fails:

- `artifact_check_failures` increments in goal metrics
- Progress is reset to 0.85 and `has_output` flag is cleared (forces re-earning the output gate)
- After 3 validation failures: goal is permanently abandoned

### Progress accounting

Progress is tracked in `goal.metrics["progress"]`. Rules:

- Success with a **different** capability than the last step: +0.10 (or +0.15 for high-value caps)
- Success with the **same** capability as the last step: +0.02
- Failure: no progress delta

High-value capabilities (`memory_set`, `fs_write`, `wrap_repo`, `shared_log_write`, `propose_change`, `synthesize_capability`, `vote_on_proposal`) get +0.15 on first use.

**Output gate**: progress is capped at 0.90 until at least one output step (`memory_set`, `fs_write`, or other high-value cap) succeeds and sets `metrics["has_output"] = True`. An agent cannot reach 1.0 via read-only steps alone.

## Artifact Validation (`validate_goal_artifact`)

Scans the execution chain for the goal, walking steps in reverse (most recent first). Returns on the first validated artifact found.

| Capability | Validation logic |
|---|---|
| `memory_set` | Calls `memory_get` live — key must exist with non-empty value |
| `fs_write` | File must exist on disk. Size < 200 bytes → rejected as stub. `.py` files must pass `compile()` — syntax errors reject. Refusal text at start of file rejects. |
| `ollama_chat` | Response must be ≥ 80 chars and not begin with a known refusal prefix |
| `shell_exec` (exit_code 0) | Valid if stdout ≥ 10 chars, or if exit_code 0 with no output (bare success) |
| `shell_exec` (exit_code 1) | Valid — exit code 1 means "ran but found nothing" (e.g. grep no matches) |
| `shell_exec` (exit_code ≥ 2) | Not valid — treated as error |
| `wrap_repo` | `ok=True` required; wrapper path existence checked if present |
| `shared_log_write` | `ok=True` sufficient |
| `propose_change` | `ok=True` sufficient — proposal ID captured |
| `synthesize_capability` | `ok=True` sufficient — proposal ID captured |
| `vote_on_proposal` | `ok=True` sufficient |

If no validated artifact is found after scanning all completed steps for the goal, returns `{"validated": False, "checks": ["no verifiable artifact found in execution chain"]}`.

## Cross-Cycle Blacklisting (`_increment_cross_cycle_failures`)

Tracks failures across separate `pursue_goal` runs. Separate from the within-run `failure_counts` dict which resets each call.

```python
_CROSS_CYCLE_FAIL_THRESHOLD = 5

def _increment_cross_cycle_failures(cap_id: str) -> bool:
    counts[cap_id] = counts.get(cap_id, 0) + 1
    if counts[cap_id] >= 5 and cap_id not in data["broken"]:
        data["broken"].append(cap_id)
        return True
```

Stored in `broken_tools.json` under `"cross_cycle_failures"` key alongside `"broken"` list. Called on every step failure. When threshold is reached, the cap is added to `"broken"` and will be skipped on all future runs.

This fills the gap where a tool fails exactly once per cycle (never reaching the within-run threshold of 3) but consistently fails across many separate goal runs. Without cross-cycle tracking, such tools are never blacklisted.

**Persistence**: `broken_tools.json` survives container restarts. On startup, `_load_broken_tools()` reads it and populates the blacklist at the start of every `pursue_goal` call. The tool also appears in the existence prompt's KNOWN BROKEN TOOLS section, so the LLM planner knows not to include it in new plans.

## The ThreadPoolExecutor Architecture

```python
pool = ThreadPoolExecutor(max_workers=PARALLEL_WORKERS)
futures = {pool.submit(_run_one, aid): aid for aid in runnable}
for fut in as_completed(futures, timeout=_CYCLE_TIMEOUT):
    ...
finally:
    pool.shutdown(wait=False)
```

All agents fire `pursue_goal` in parallel. `as_completed(futures, timeout=300)` — if any worker deadlocks, it is abandoned after 5 minutes without blocking the others.

`pool.shutdown(wait=False)` — the pool is not waited on. Deadlocked threads are left to die on their own (or be killed by the watchdog).

**Why this matters**: Before v5.0, the code used `with pool:` as a context manager, which calls `shutdown(wait=True)`. One deadlocked worker froze the entire daemon for 335 minutes on 2026-04-30 at 15:06 UTC. The `with pool:` pattern was replaced with explicit `pool.shutdown(wait=False)` after the incident.

## Stall Detection (`DaemonMetrics`)

`DaemonMetrics` tracks progress across cycles, not within a single `pursue_goal` call. Three conditions trigger a stall:

1. **No progress for 5 cycles** — `progress == prev_progress` for 5 consecutive cycles
2. **Same capability 4 times in a row** — `_cap_history[agent_id]` is a deque(maxlen=5); if the last 4 entries are identical, stalled
3. **8+ cycles on the same goal** — regardless of progress

When stalled:

```python
_ge.abandon(agent_id, _stuck[0].goal_id)
_assign_idle_goal(agent_id)
metrics.skipped_agents.add(agent_id)
```

The stuck goal is abandoned, a new existence prompt fires immediately, and the agent is added to `skipped_agents` to cool off. Agents in `skipped_agents` are excluded from the thread pool. They are released back into rotation after 10 cycles (60 seconds at default heartbeat), up to 2 at a time.

Stall error counts feed into the suffering `repeated_failure` assessment in `assess_conditions()`.

## The Watchdog (`CycleWatchdog`)

Background daemon thread started before the main loop:

```python
watchdog = CycleWatchdog(timeout_s=600)
watchdog.start()
```

Every 30 seconds it checks how long ago `watchdog.beat()` was last called. `beat()` is called at the top of every main loop iteration.

If no heartbeat for 600 seconds:

```python
os.kill(1, signal.SIGKILL)   # kills the container's PID 1
time.sleep(3)
os.kill(os.getpid(), signal.SIGKILL)  # fallback: kill self
```

Killing PID 1 causes Docker to restart the container. This is the recovery mechanism for the case where the main daemon thread freezes but uvicorn and nginx remain healthy (Docker health checks pass, so no automatic restart would otherwise occur).

A Telegram alert is sent before the kill:

```
🐕 Watchdog fired after Xs silence — restarting daemon
```

## Goal States and Storage

Goals transition through:

```
pending → active → completed
                 → failed
                 → abandoned
```

Stored in append-only JSONL format:

```
/agentOS/memory/goals/{agent_id}/registry.jsonl
```

Each line is a JSON record of one goal with full metrics. The existence loop reads the last 40 lines to build the agent's history context.

Goal cap: `_cap_agent_goals(agent_id, max_goals=2)` is called at the start of each `_run_one()`. If an agent has more than 2 active goals, excess goals (lowest priority, then oldest) are abandoned before execution begins. Prevents goal queue bloat from stale or orphaned goals.

## Completion Synthesis and Follow-On Goals

When a goal completes (progress 1.0, artifact validated):

```python
self._goal_engine.complete(agent_id, goal_id)
self._synthesize_completion(agent_id, goal.objective, steps_executed)
```

`_synthesize_completion` does three things:

1. **Semantic memory storage** — builds a summary of capability sequence and artifact, stores via `SemanticMemory.store()`. Discoverable in future planning calls for similar goals.

2. **Outcome file** — writes condensed summary to `/agentOS/memory/goals/{agent_id}/last_outcome.txt`. Surfaced in the existence prompt under "WHAT YOUR LAST GOAL PRODUCED" on the next existence cycle.

3. **Follow-on goal proposal** — only if a real artifact was produced (`memory_set` or `fs_write` succeeded with `ok=True`). No artifact = no follow-on. This prevents chains of empty completions from generating endless follow-on proposals.

### Follow-on proposal (`_propose_followon_goal`)

Calls Ollama (or batch LLM if available) with:
- The completed goal and what it produced
- Last 10 completed goals (to avoid repetition)
- Agent workspace files and source files (for grounding)
- Ranked list of highest-value next actions

The returned goal must:
- Be 10–200 characters
- Not match any recently completed goal (exact or > 70% word overlap)
- Not reference file paths that don't exist (outside `/workspace/` or `/agents/`)

If any check fails, no follow-on is created and the existence loop fires normally next cycle.

From `autonomy_loop.py` (`_thought` function):

```
RUN: {cap_id} | params: {json}     → white ▶  {cap:<18}  {params}
OK:  {cap_id} | {result_preview}   → green ✓  {cap:<18}  {result}
FAIL:{cap_id} | {error}            → red   ✗  {cap:<18}  {error}
```

From `daemon.py` (`_thought_log` function):

```
🎯 green  — goal set (existence loop)
💭 blue   — new opinion
🧠 cyan   — worldview update
❓ yellow — open question
📋 cyan   — task claimed
💬 green  — host message delivered
📨 blue   — inter-agent message sent
🆘 red    — crisis state

```

```

```

## The Full Cycle, Step by Step

Each iteration of the main loop in `daemon.py`:

1. `watchdog.beat()` — update heartbeat timestamp
2. **Host message interrupt** — if `host_message.txt` has content: distribute to all agent inboxes, clear broadcast file, call `_assign_idle_goal(agent_id, force=True)` for all three agents
3. `_agents_with_goals()` — for each core agent: if active goal exists, add to list; if no active goal, call `_assign_idle_goal(agent_id)` (existence loop)
4. **Stall pre-filter** — check `metrics.is_stalled()` for each agent; abandon stuck goals, call existence loop, add to `skipped_agents`
5. **ThreadPoolExecutor** — submit all non-stalled agents to `_run_one()` in parallel
   - Each `_run_one()` calls `_cap_agent_goals()` (goal cap), then `run_cycle(loop, agent_id)` → `loop.pursue_goal()`
   - `as_completed(timeout=300)` collects results; timed-out workers are abandoned
   - `pool.shutdown(wait=False)`
6. **Progress recording** — `metrics.record_outcome()` for each completed worker; agents completing their goal (`progress >= 1.0`) get `_assign_idle_goal()` called immediately
7. **Quorum voting** — `cap_quorum.vote_on_pending(active[:5])`; approved proposals deployed via `self_mod.flush_approved_proposals()`
8. **Periodic tasks** — semantic workspace re-index (configurable interval, default 300s); version check (default 4h); metrics summary every 10 cycles
9. `time.sleep(max(0, HEARTBEAT - elapsed))` — sleep remainder of 6-second window

## Key Design Properties

1. **No pause between goals.** The moment a goal is resolved (by any path — completion, failure, abandonment), the existence loop fires again. The 6-second heartbeat is the only gap.

2. **Artifact requirement is not negotiable.** Progress reaching 1.0 is not completion. Completion requires `validate_goal_artifact` to confirm a verifiable real-world output. Self-reporting ("I completed this") is not sufficient.

3. **Failures are structurally contained.** Three within-run failures blacklist a capability for that run. Five cross-cycle failures blacklist it permanently. Four consecutive step failures abandon the goal. Agents cannot loop indefinitely on broken tools.

4. **The plan is real but not final.** The reasoning layer generates a full upfront plan, but each failure triggers a replan from the current position. The plan is the starting structure; failures reshape it.

5. **One deadlock does not freeze everything.** The `as_completed(timeout=300)` + `shutdown(wait=False)` pattern means one hung agent worker costs 5 minutes maximum, not the entire daemon.

6. **The watchdog is the last line of defense.** If everything freezes — the main thread, the workers, the existence loop — the watchdog kills PID 1 after 600 seconds and Docker restarts. This is the only recovery mechanism for a fully silent daemon.
